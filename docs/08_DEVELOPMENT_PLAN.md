# 开发计划

本文是基于当前代码和产品目标的增量计划。每个阶段都应保持应用可运行，不采用整套重写。

## 1. 开发原则

1. 用户现有数据库优先，Schema 变更必须可迁移、可验证、可恢复。
2. 先修正现有数据口径和分层，再扩展复杂分析。
3. 每个功能同时考虑 UI、service、数据库、测试和文档。
4. 目标功能没有完成前，不在界面或 README 中声称已可用。
5. 不引入当前规模不需要的微服务、队列、缓存或 AI 编排。

## 2. P0：建立可靠核心闭环

### P0-1 数据安全与迁移基线

交付：

- 增加数据库 Schema 版本记录；
- 提供备份、恢复和升级前检查流程；
- 用真实结构的数据库副本执行迁移测试；
- 首次初始化与已有用户升级使用不同路径。

验收：旧数据库升级后表和数据数量正确，应用和核心测试通过，失败可恢复到备份。

### P0-2 修复现有明确问题

交付：

- 阅读“今日分钟”按日志日期计算；
- 主任务选择排除已完成/放弃任务；
- 清理页面中的异常转义字符；
- 统一保存错误反馈；
- 检查默认目标与任务种子，避免替用户预设人生方向。

### P0-3 Daily Journal 最小版本

交付：

- 新建日记数据模型和 service；
- 支持按日期保存、读取、列表浏览；
- 保留现有 `daily_reviews`，提供清晰的兼容关系；
- 至少支持空状态、保存状态和历史入口。

### P0-4 Quick Capture 收件箱

交付：

- 快速保存未分类文字；
- 查看未处理列表；
- 转为任务、转为日记或归档；
- 转换过程事务化，任何失败不丢原文。

## 3. P1：补齐管理和反馈能力

### P1-1 Goal History

- 目标重要修改自动留版本；
- 支持变更原因、归档和历史查看；
- 周/月生成轻量进度快照；
- 旧任务关联持续有效。

### P1-2 习惯与书籍完整管理

- 习惯编辑、停用、安全删除；
- 书籍新增、编辑、排序、归档；
- 删除前展示受影响日志数量；
- 统一通过 service 写数据库。

### P1-3 统计与周复盘

- 睡眠、习惯、阅读趋势；
- 目标进度变化；
- 周复盘视图；
- 每个指标显示统计日期和计算口径。

### P1-4 搜索、导出与恢复工具

- 搜索日记、捕获、任务；
- 导出 CSV/Markdown/JSON；
- UI 或脚本化备份检查；
- 恢复仍需明确确认，避免误覆盖。

## 4. P2：可选增强

- 操作系统级提醒；
- 移动端体验优化；
- 数据可视化深化；
- 用户明确授权后的 AI 总结、任务拆解或周复盘建议。

AI 只能提供建议，不控制认证、删除、状态机或未经确认的数据写入。发送给模型的数据范围必须可见、可选、可关闭。

## 5. P3：出现真实需求后再评估

- 多设备同步与冲突解决；
- 登录、权限和远程 API；
- 多用户；
- 外部日历或任务系统集成；
- Agent 自动工作流。

这些能力会明显增加隐私、部署和维护成本，不属于当前本地个人工具的默认路线。

## 6. 每项工作的完成定义

```text
需求与状态更新
→ 数据模型/迁移完成
→ Service 规则完成
→ UI 可用且状态明确
→ 正常/异常/边界测试通过
→ 旧核心流程回归通过
→ 文档、CHANGELOG 同步
→ 给出用户可执行的验收步骤
```

## 7. 建议的开发切片

一个切片控制在能独立验证的范围。例如 Quick Capture 可拆为：建表与迁移、service 测试、收件箱 UI、转任务事务、转日记事务、搜索与归档。不要同时改造全部页面。
